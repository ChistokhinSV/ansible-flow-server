# Changelog

All notable changes to Ansible Flow Server.

## Unreleased — first version

Nothing is released yet.

### Added

- Lists of runs are columns: state first, then the run, its launch configuration, mode, who started it, when, and the commit, so a list can be read down a column. On a phone or in a narrow pane a run is two lines.
- Pages to work on use the width of the screen. An execution environment shows what runs get now beside a wide spec: collections are a table of names and versions with one line to find or add one, Python and Debian packages are side by side, the base image and certificate authorities are folded, and Delete is the last section. A project's Files is one of its tabs: a bar with the branch and what adds files, the tree, and the file beside it as tall as the window; the README or the first file is open when you come. A launch configuration's settings are rows of two fields with one chooser for the execution environment (the server's default, an environment, or an image by name).
- The runs list has a Mine choice and, for a chosen project, a choice of one of its launch configurations; both are kept in the address. A launch configuration's Runs tab lists all of its runs, older ones a page at a time. A project's Overview says how each flow's last run went, with a link to the run. Over the API, runs are filtered by launch configuration (`config`) and by who asked for them (`by`), and paging no longer skips runs made at the same moment; launch configurations and a project's flows say their newest run (`lastRun`); administrators read what one person reaches (`GET /users/:id/access`) and where a group is named (`GET /groups/:id/grants`) in one request. Agents get the same in `run_list` and `launch_config_list`. See [Runs](README.md#runs).
- The pages are arranged by what people do on them; long pages are split into tabs, each with its own address. A workspace has Projects, Execution environments, Credentials and Access (who can do what comes first). A project shows its state in one line and has Overview (launch configurations with their last run and a Launch button, flows, the newest runs), Runs, Files, Branches and Settings. A launch configuration has Launch (the form and the button on top), Runs, Schedules and Settings. A flow's page links to its launch configurations and newest runs, and Home lists the configurations you launched lately. A run's page leads through its workspace, project and launch configuration, shows the hosts with a problem first and has a button to its output; the runs list filters by project and loads older runs. The administration's pages are in the side menu: People and Groups are tabs with adding behind a button, a person's page shows what they reach in each workspace, the certificate page shows the certificate and its history before the ways to replace it, Notifications opens on the delivery log, and My account has Profile and Access tokens. See [The web pages](README.md#the-web-pages).
- Every page now has the new look: workspaces, projects and the administration's pages are rows divided by thin lines; runs are rows with their state in words and are filtered with a row of choices; approvals waiting for you are each a tinted box with the decision in it, others' are rows with why not; forms being filled in sit on a quiet surface. See [The web pages](README.md#the-web-pages).
- A new look for the pages: dark by default with a light theme beside it (the theme button goes dark, light, as the device), calm flat sections, and colour only where something needs you. A side menu replaces the top bar, with the count of approvals waiting for you and your workspaces. Sign-in is a card over a picture of a flow. A new Home says how the day went, lists the approvals waiting for you, the latest runs and the workspaces; the workspaces list moved to `/workspaces`. A run's page shows the run on its canvas with, beside it, the approval that waits, its hosts with problems first, and why a host failed. See [The web pages](README.md#the-web-pages).
- A flow library: an administrator makes a project a library, and its flows' subflows are offered to every project (to people who may read the library's workspace) on a new Library page and in **Insert Shared Subflow…** while editing a flow in the pages. A copy is pinned to the library flow's version and commit; a flow's page lists its library copies and which are behind, with **Update** while its draft is edited. The same over the API. See [Flow library](README.md#flow-library).
- A project's files in the pages: **Files of the project** shows the tree of a branch; read and download any file, edit text files with highlighting, add, upload (also a folder as zip), move and delete files and folders. The changes are kept until **Save**, one commit on the branch by you; it goes on top of a branch that moved, and is refused with the files listed when the branch changed the same files. The same over the API. See [Files of a project](README.md#files-of-a-project).
- Runs find the repository's own modules (`library/` with `module_utils/`), plugins (`filter_plugins/`, `lookup_plugins/`, `test_plugins/`, `action_plugins/`), the callbacks its `ansible.cfg` enables, and `group_vars/` and `host_vars/` at the repository root, as runs from VS Code do; a relative file a step reads is the repository's. See [Runs](README.md#runs).
- The server certificate's private keys are kept sealed with the master key in the data folder, so a copy of the folder without the master key does not give them away. Keys kept plain by an older version are sealed at the next start, and `secrets rotate` seals them again. Keep the master key outside the data folder for this to help. See [HTTPS and the certificate](README.md#https-and-the-certificate).
- Push hooks from GitHub: the hook's token is GitHub's webhook secret, and the server checks GitHub's signature of each call. A project's page has a **Push hook** section to set one up (the address and token shown once, with how to enter them at GitHub, GitLab and Gitea), make a new token or remove it. See [Workspaces and projects](README.md#workspaces-and-projects).
- A project's source over SSH signs in with an SSH key from the workspace's credentials, with or without a passphrase, for reading it and for passing pushes on. SSH host keys are trusted on first use and kept in the data folder; the project's page shows the fingerprint, and a host that shows another key later stops the project until an administrator accepts the new key. See [Credentials and the master key](README.md#credentials-and-the-master-key).
- Manage a project's branches on its page and over the API: each with its newest commit and the commits not on the project's branch; make one from a branch or a commit, delete one, and (administrators) make another the branch that runs. For a project with a source the change is made at the source. The branch that runs and branches launch configurations use are not deleted, and a branch with unmerged commits is deleted only when you confirm. See [Branches](README.md#branches).
- Start a project the server hosts from a sample project (Hello, Edge baseline, Firewall upgrade) or from an archive of your files (zip or tar.gz), when adding it or on its page while it is empty; the same over the API. Archives are checked before anything is committed: no paths outside the project, no links, no `.git` folder, at most `AFS_ARCHIVE_MAX_MB` unpacked. See [Starting a hosted project from a sample or an archive](README.md#starting-a-hosted-project-from-a-sample-or-an-archive).
- Install a server certificate from a PFX (PKCS#12) file: `cert install <file.pfx> --passphrase-file <file>`, a PFX upload with its passphrase on the Server certificate page, and the same over the API. The certificate, its chain and its key go through the usual checks; the passphrase is never an argument or a log line and is kept nowhere. See [HTTPS and the certificate](README.md#https-and-the-certificate).
- Edit flows in the pages, together: **Edit** on a flow's page opens the designer in full. Everyone editing one flow edits one shared draft and sees the others' changes at once, with who is here and what they changed; Ctrl+Z takes back your own last edit; **Save** makes one commit on the branch with everyone who edited as co-authors (merged step by step when the branch moved, conflicts listed); **Discard** drops the draft. Binding a step searches the module catalog read from the flow's execution environment image. See [Editing flows in the pages](README.md#editing-flows-in-the-pages).
- When someone changes a flow you have open, a bar on the canvas says who and how much, with Show changes (the Changes lens against the version you had) and Update. The Changes lens compares with any earlier commit of the flow, and a project's page lists the flows changed while it is open. The same over the API: a project's event stream, the changes between two commits, and a flow's history. See [The web pages](README.md#the-web-pages).
- Sign in with a directory (LDAP, Active Directory): people type their directory login and password in the usual form. Administrators add directories on the Sign-in page from an Active Directory or OpenLDAP preset, map the directory's groups (nested AD groups too) to server groups or administrator, and test a login. A sync on a timer disables people who left the directory or were disabled in Active Directory, and their open sessions stop at once; a directory that does not answer disables nobody. See [People, groups and sign-in](README.md#people-groups-and-sign-in).
- Sign in with your organisation (OIDC: Keycloak, Entra ID, Google and others): administrators add providers on the new Sign-in page, with what the provider's groups are here (server groups or administrator). People are made at their first sign-in; their groups follow the provider at each sign-in, while what was set here by hand stays. Passwords can be kept for administrators only. See [People, groups and sign-in](README.md#people-groups-and-sign-in).
- Operations: `/metrics` for Prometheus (runs by state, queue depth, run and build durations, approvals waiting, notification deliveries, certificate expiry, requests), behind `AFS_METRICS_TOKEN`; `/readyz` says ready, degraded or unavailable check by check (database, data folder, disk space, container engine); `backup` and `restore` commands that take everything the server keeps while it runs and restore it into SQLite or PostgreSQL; an upgrade guide. See [Operations](README.md#operations).
- Install as a Linux service: a bundle per architecture (x64, arm64) with the server and Node.js on each release, and `install.sh`, which installs, upgrades (settings and data kept) and removes it as a systemd service. Runs use rootless podman as a service user of their own, or docker. SELinux systems are set up for it. A command line, `ansible-flow-server`, manages users, certificates and secrets. See [Install as a Linux service](README.md#install-as-a-linux-service).
- Run with docker compose: the server image (GitHub's registry and Docker Hub, amd64 and arm64, published for each release), a compose file with SQLite by default and a PostgreSQL profile, and an `.env` example. Runs start as sibling containers through the engine's socket; the data may be any volume, since the server finds where the engine has it (or `AFS_ENGINE_DATA_DIR` says). See [Run with docker compose](README.md#run-with-docker-compose).
- The server speaks HTTPS itself. At first start it makes a self-signed certificate; the `cert` commands request a certificate from your authority, install one, roll back, or make a new self-signed one, and the server uses a new certificate without a restart. Behind a proxy that does HTTPS, set `AFS_TLS=off`. See [HTTPS and the certificate](README.md#https-and-the-certificate).
- A Server certificate page for administrators, and the same actions over the API: the certificate in use with its days left, a request made and downloaded for your certificate authority, the signed certificate installed (or replaced with a certificate and key), a new self-signed one, a rollback, the history. A refused certificate is shown with every reason. Administrators see a banner on every page while the certificate has 30 days or fewer left.
- Settings from the environment or a `.env` file; SQLite by default, or PostgreSQL with `AFS_DATABASE_URL`. See [Configuration](README.md#configuration).
- People and groups, with sign-in by password. The first administrator is made with a setup code from the server's log, or with `user add --admin` on the server's machine. See [People, groups and sign-in](README.md#people-groups-and-sign-in).
  - After five wrong passwords for a login in fifteen minutes, sign-in for it waits.
  - The `user` commands set a password, enable, disable and make administrators when nobody can sign in.
- Personal access tokens for programs (git, scripts, the VS Code extension): sent as a bearer token or as the password of a git sign-in. A token can be read-only, expires (90 days unless set), and cannot make tokens or set passwords. See [Access tokens](README.md#access-tokens).
- Workspaces and projects. A project is a git repository: one the server keeps, or an existing one the server mirrors and looks at on a timer, on request, or when the git host calls the project's push hook. See [Workspaces and projects](README.md#workspaces-and-projects).
- Every project can be cloned, fetched and pushed through the server, signed in with an access token. A push to a project with an external repository is passed on to it and accepted only if that repository accepts it. The project's branch cannot be deleted or rewritten through the server. Who pushed what is listed per project.
- Web pages at the server's address: first-run setup, sign-in, workspaces, projects with their state, branches, flows and pushes, and your access tokens. Light and dark, at phone width too. See [The web pages](README.md#the-web-pages).
- Pages for people and groups, for administrators: add people, administrators and service accounts; change their profile, make or unmake administrators, disable, set a password, see and revoke tokens (and make them for a service account), delete; add, rename and delete groups, set their email address, webhook and members. See [The web pages](README.md#the-web-pages).
- A project's flows are listed with their errors and warnings, and a flow opens on the designer's canvas, read-only.
- Run on a flow's canvas opens the designer's launch dialog over one of the flow's launch configurations: its start values, the inventory's groups, and the hosts the targets match, counted again as you type; Run launches it and shows the run on the canvas.
- A launch configuration's page shows the hosts a launch would touch, read from the inventory in the launch's image: how many, which names the inventory does not have, and what looks like production. Also over the API: `POST /api/v1/launch-configs/:id/facts`. See [Launch configurations](README.md#launch-configurations).
- Credentials kept encrypted with a master key outside the database: SSH keys, logins, become passwords, vault passwords, git tokens, registry sign-ins and environment variables. A secret goes in and is never shown again. `secrets status` and `secrets rotate` manage the key; rotating seals again every secret the server keeps, runs' inputs included. See [Credentials and the master key](README.md#credentials-and-the-master-key).
- Runs use SSH keys with a passphrase: the key is unlocked into an ssh-agent inside the run, and a wrong passphrase fails the run with a clear reason. A registry credential signs in to the image's registry and pulls a private image before the run, without touching the engine's own sign-ins.
- A workspace's page lists its credentials, what each holds and how much uses it; administrators add one with a form for its kind, change it, replace its secret (never shown, not filled in by the browser; a private key from a file) and delete one nothing uses. An external project chooses its git sign-in when added and on its page, and says when its source asks for one.
- A project with a private repository over HTTPS signs in to it with a git token or login credential, also when passing pushes on.
- Launch configurations: a flow with its inventory, execution environment, check or real mode, limit, start values and credentials, saved only if it could run. Ask what a launch would run (commit, inputs, hosts) before running it. By default the newest commit of the project's branch runs; a launch can name another branch or a commit. See [Launch configurations](README.md#launch-configurations).
- Launching puts a numbered run in a queue kept in the database; runs can be listed and cancelled. At most `AFS_MAX_RUNS` runs at once (4), and `AFS_MAX_RUNS_PER_PROJECT` of one project (1). See [Runs](README.md#runs).
- The server runs flows: Ansible in an execution environment container (docker or podman), the same way VS Code runs them. See [How a run is run](README.md#runs).
  - The repository at the run's commit, with the flow's code generated fresh from the flow.
  - The image from the launch configuration, else `AFS_EE_IMAGE`. With no container engine, runs wait in the queue.
  - SSH keys, login and become passwords, vault passwords and environment variables from the credentials store; secret values are hidden in the output.
  - A run's output and how it went, step by step, are kept; a run longer than `AFS_RUN_TIMEOUT_MINUTES` (240) is stopped.
  - The server can itself run in a container, with the engine's socket.
- Runs can be watched as they go. See [Runs](README.md#runs).
  - **Runs** page: every run, filtered by state. A project's page lists its recent runs.
  - A run's page: what ran, the run on the flow's canvas live (hosts through each step), and Ansible's output as it comes. Administrators can **Stop** a run and **Run again** an ended one with the same commit, inputs and credentials.
  - On the canvas, a step's host output, the flow's earlier runs and Stop work as in VS Code.
  - Scripts can follow a run with `GET /api/v1/runs/<id>/events` (server-sent events).
  - Ended runs are removed after `AFS_RUNS_KEEP_DAYS` (90), and beyond `AFS_RUNS_KEEP_PER_FLOW` (200) of one flow.
- `/api/v1/meta` says which flow formats the server reads, what a client may rely on (`features`) and which designer canvas the pages carry. See [Compatibility with the designer](README.md#compatibility-with-the-designer).
- Search in the top bar of every page (`/` or Ctrl+K): workspaces, projects, flows, launch configurations, runs (by number too), environments and settings pages as you type, only what you may see; people and groups for administrators. See [The web pages](README.md#the-web-pages).
- A launch configuration's page shows what its flow needs (the collections its steps run, and the project's `collections/requirements.yml`) against what its environment's image holds, and makes an environment for the flow in one step. Collections can be searched on Galaxy, or the configured hub, when writing a spec. See [Execution environments](README.md#execution-environments).
- Execution environments: a workspace keeps the images its runs happen in, built by the server from a spec (ansible-core, collections with a version, a range or latest, Python and Debian packages, certificate authorities) or an image that exists already. A build settles versions into a lock, reads what the image really holds, keeps a log, and old images are removed. A launch configuration chooses an environment and gets its newest good build. The same environment can be taken to AWX or AAP as an ansible-builder file. See [Execution environments](README.md#execution-environments).
- Schedules: a launch configuration runs by itself on a cron in a time zone, or once at a set time, as the schedule's owner, whose access is checked each time. A schedule has its own mode, input values and optionally a pinned commit; after downtime it runs once or skips; while its last run goes it skips or queues. Its page shows the next times and how the last fire went; administrators can hand a schedule to a service account. See [Schedules](README.md#schedules).
- Dev runs: someone who may push sends work they have not pushed yet, committed or not, and the server checks it with the flow's launch configuration, in check mode only. The work is kept a day under a ref nobody else sees and never reaches a branch or an external source; the run is marked a dev run. See [Dev runs](README.md#dev-runs).
- Agents (Claude Code, Codex, Cursor) use the server over MCP at `/mcp`, signed in with an access token. See [Agents (MCP)](README.md#agents-mcp).
  - They read the projects' flows with the designer's flow tools, and list, check, launch, follow and stop runs, seeing and doing only what the token's owner may.
  - Approvals stay with people: an agent decides one only with a token made to allow it.
  - What an agent changes is in the audit log as coming from an agent.
- Notifications by email and webhook. See [Notifications](README.md#notifications).
  - Approvers are asked when a run waits for them; who launched a run is told when its approval is approved, rejected or times out; the approval's `notify` list is told of both.
  - A launch configuration can tell people and groups when its runs fail, or whenever they end.
  - Everyone sets their own email address on My account; webhooks are set by administrators.
  - Administrators are told as the server certificate nears its end (30, 14, 7, 3 and 1 days before, and once it has ended).
  - Email through a mail server set on the new Notifications page; its password is kept encrypted. Webhooks get the event as JSON with a `text` line for chat tools, signed with a key administrators make.
  - Messages are tried again when the mail server or receiver is busy or unreachable, survive a restart, and are listed in a delivery log with Try again. A message never holds a run's inputs or a secret.
- Approvals: a flow with approval steps stops at each one until someone allowed decides, then goes on with the hosts that waited. See [Approvals](README.md#approvals).
  - Whoever has the `approve` grant decides; when the approval names its approvers in the flow, only they. Who launched the run does not, unless the workspace allows it.
  - Decide with a comment on the **Approvals** page, on the run's page, on the canvas, or over the API. Who decided, when and why is shown with the run and kept in the audit log.
  - An approval with a timeout that nobody decides in time sends its hosts through its timeout port.
  - A waiting run holds no container, and still waits after the server restarts.
  - The `approve` grant lets its holder see the flows and runs they decide.
- Access levels: administrators give a user or a group `ro`, `operator`, `rw` or `approve` on a whole workspace or on one flow, on the workspace's page or over the API. See [Access levels](README.md#access-levels).
  - `ro` sees the workspace's projects, flows, launch configurations and runs, and clones; `operator` also launches as a configuration says and stops runs; `rw` also launches another branch or commit, manages launch configurations and pushes through the server.
  - A grant on one flow replaces the workspace's for that flow; the highest of a person's own and their groups' grants counts.
  - **Who can do what** on the workspace's page lists every person with access as their grants come out.
  - People who are not administrators now see only what they were given: give grants after upgrading.
- The API is described as an OpenAPI 3.1 document at `/api/v1/openapi.json`, and the **API reference** page shows it by subject: what each address does, who may call it, what it takes. See [The API](README.md#the-api).
- Service accounts: an identity for a pipeline or program, with no password, signed in only with tokens an administrator makes for it (`"service": true`, or `user add --service`). See [Service accounts](README.md#service-accounts).
- An access token can be limited to one workspace: it reaches that workspace's projects, credentials, launch configurations, runs and repositories, and nothing that spans workspaces. Choose it when making the token, or `user token --workspace`.
- Launching from the pages. See [Launch configurations](README.md#launch-configurations).
  - A project's page lists its launch configurations; administrators add, change and delete them, choosing the flow, branch or pinned commit, inventory, image, mode, limit and credentials.
  - A configuration's page has the launch form: the flow's inputs (secret ones typed hidden and never kept), check or real, another branch or a commit, and the limit.
  - **What would run** shows the commit, inputs and hosts before anything runs, with any problem shown at its field. **Launch** starts the run and opens its page. **Keep as start values** saves the typed values as the configuration's.
- An audit log of who did what and when: sign-ins (refused ones too), tokens, people and groups, workspaces, projects, credentials, launch configurations, runs launched, stopped and run again, pushes (refused ones too), and the server's `user`, `cert` and `secrets` commands. See [The audit log](README.md#the-audit-log).
  - Each entry names who, from where (pages, API, git, server command), what, to what, and how it ended. No secret values are kept.
  - Administrators read it on the **Audit log** page, filtered by person, subject, result, source and dates, and export it as CSV or JSON; `GET /api/v1/audit` for scripts.
  - Entries are kept for `AFS_AUDIT_KEEP_DAYS` (365); `0` keeps them all.
- Running a flow from its canvas: the choice of launch configuration also offers New configuration…, which opens the page that adds one for this flow (also when the flow has none yet). The canvas's launch dialog has Save as Launch Configuration…: a new configuration like the one chosen, with the dialog's mode and inputs (secret inputs are never kept). On a launch configuration's Launch tab, host lists suggest the inventory's groups; under Settings, Whom suggests the server's people and groups.
- Administrators delete a project on its Settings tab and a workspace on its Access tab, after typing its key; what goes with it is said first, and a refusal (a run going, a workspace not empty) is shown.
- My account has a Password section: change your own password (your other sessions are signed out).
- Flows are made, copied and deleted in the pages: New flow on a project's Flows (the designer's starting flow, opened on its page), Copy the flow… and Delete the flow… in the More (⋯) menu of a flow's page (the copy gets its own id and key; Delete says which launch configurations run it). Each is one commit on the project's branch, for people with rw on the workspace.

### Changed

- A check (skeleton) run passes its approvals by itself, as a skeleton run in VS Code does, and notifies nobody; only real runs wait for the approvers.
- Built on Ansible Flow Designer 0.86.0.
- Clearer pages: every approval waiting for you is tinted on Home, waiting is amber on the approvals pages too and Reject reads clearly beside Approve; the day's line on Home says how many runs failed and wait, not only how many went well; New branch, Make a token and Add a directory sit at the head of their sections; Keep as start values, To the output and a file's Download are buttons; a launch configuration's notification fields are Notify when and Recipients; the commit message field of a flow being edited is labelled; an empty library says how a project becomes one; an empty reason in the notifications log shows a dash.
- The top bar is as wide as the page under it, so the search box ends where the page does, and a page's breadcrumbs sit in the bar beside it instead of a row of their own. On a flow's page, Full screen (the canvas, viewing or editing) and Open on its own page (with the draft while editing) are icon buttons beside Edit.

### Fixed

- Stopping a run that waits for approval ends it on its canvas too: the run says who stopped it instead of waiting, and the approval says who cancelled it.
- Fields side by side stay on one line when the hint under one of them wraps.
- A workspace's Add project button shows on its Projects tab only.
- Finding a collection for an execution environment lists the collection named by the words first, and finds a full name such as `fortinet.fortios`, which found nothing before.
- An execution environment's page says under its title how the newest build went: built and whether runs get its image, failed and what runs get meanwhile, or still going; whether the spec changed since, and whether building again can bring newer versions. The button reads Build again once built.
- Building an execution environment while its spec has changes not saved no longer builds the old spec without a word: the page says the changes are not saved, and the button reads Save and build, which saves them first.
- The ansible-builder file of an execution environment follows its saved spec: collections added since the last build are in it, given as the spec writes them; collections the last build installed stay pinned to that version while it still meets the spec. With changes not saved, the page's link reads Save and get ansible-builder file and saves them first.
- Show Terminal on a run's canvas goes to the run's output without loading the page again, and outlines it for a moment; from elsewhere it opens the run's page at its output. The output is headed Terminal output and shows Ansible's colours and bold text; All of it as text and agents still get plain text.
- The suggestions for host lists and Whom show: they keep what is already typed in the field, so a field that starts filled (`all`, `olga`) offers the rest after it. A host list also shows the inventory's groups as buttons under the field, read when the Launch tab opens; a button adds its group or takes it out.
- Approvers see the runs of the workspaces and flows they approve in run lists (Runs, Home, a project's recent runs, the canvas's earlier runs); before, only one run at a time could be opened.
- The Add project form no longer stays open over a workspace's other tabs, and the search box empties when another page opens.
- A workspace's Access tab and the administration pages say they are for administrators to someone else, instead of an empty page or Nothing here.
- Pages line up: the dot between items of a status line is no longer underlined with the link after it, a page head's buttons and links are centred, filter choices are as tall as the box beside them, the e-mail settings' two buttons sit side by side, the audit log's Since and Until stay together, API rows that do not open line up with those that do, and the sign-in title does not leave one word alone.
- A project's page no longer draws two lines with nothing between them where one section ends and the next begins.
